## 1. Résumé exécutif

La plateforme est **fonctionnellement très complète et techniquement saine sur le fond**. Le typage passe sans erreur, le lint est propre, et le contrôle d'accès serveur est appliqué de façon systématique et cohérente sur toutes les routes sensibles — ce qui est rare sur un projet de cette taille.

Les problèmes ne sont **pas dans le code métier, mais dans la chaîne d'exploitation** : l'environnement de développement local est branché sur la base de production, les tâches planifiées ne s'exécutent jamais, et la moitié des intégrations externes n'ont pas de clés en production.

## 3. Constats bloquants (P0)

### 🔴 P0-1 — L'environnement de développement local est branché sur la base de production

**Fichier** : `.env`

```
DATABASE_URL="postgresql://***@byjpfecdckni2j5rcadm-postgresql.services.clever-cloud.com:50013/..."
APP_BASE_URL="https://finarent.com"
AUTH0_BASE_URL="https://finarent.com"
```

Le fichier `.env` chargé par défaut en local contient **la chaîne de connexion PostgreSQL de production** et les URL du domaine public.

**Conséquences directes :**

- `npm run dev` lit **et écrit** les vraies données clients.
- `npm run db:migrate` exécute `prisma migrate dev`, une commande qui **propose de réinitialiser la base** dès qu'elle détecte une dérive de schéma. Un « oui » par réflexe efface la production.
- `node scripts/seed-demo.js` commence par des `deleteMany({})` sur `Commission`, `StatusHistory`, `Message`, etc. **Lancé en l'état, il détruit des données de production.**
- Les URL de retour Auth0 pointant sur `https://finarent.com`, un test de connexion local renvoie l'utilisateur sur le site en ligne.

**Correction :**

1. Créer une base locale (PostgreSQL via Docker, ou une branche de base dédiée).
2. Sortir la configuration de production du fichier de travail (elle vit déjà dans la console Clever Cloud) et remplacer `.env` par une configuration locale : `DATABASE_URL` local, `APP_BASE_URL=http://localhost:3000`.
3. Ajouter un garde-fou en tête de `scripts/seed-demo.js` et `scripts/test-e2e.js` : refuser l'exécution si `DATABASE_URL` contient un hôte de production.

---

### 🔴 P0-2 — Les tâches planifiées peuvent échouer sans que personne ne le sache

**Fichiers** : `.env`, `clevercloud/cron.json`, `lib/cron-auth.js`

Les trois tâches sont **bien déclarées** pour Clever Cloud dans `clevercloud/cron.json` — ce point est en place. Le problème est ailleurs, et il est double.

**1. Le secret n'est pas dans la configuration consultable.** `lib/cron-auth.js` est volontairement *fail-closed* :

```js
export function isCronAuthorized(request) {
  const secret = process.env.CRON_SECRET;
  if (!secret) return false;   // pas de secret = accès refusé
  ...
}
```

`CRON_SECRET` figure dans `.env.example` et `.env.vercel`, mais **pas dans le `.env` actif**. Sa présence côté console Clever Cloud n'est pas vérifiable depuis le dépôt : **c'est le premier contrôle à effectuer**. S'il est absent, les trois routes renvoient `401` et aucune tâche ne s'exécute.

**2. L'échec est silencieux.** Les trois entrées de `clevercloud/cron.json` utilisent :

```
curl -sS -m 60 -H "Authorization: Bearer $CRON_SECRET" http://localhost:8080/api/cron/reminders
```

`curl` sans `-f` **sort en code 0 sur une réponse HTTP 401**. La tâche est donc considérée comme réussie alors qu'elle n'a rien fait. Aucune alerte, aucune remontée — il faut ouvrir les journaux et lire le corps de la réponse pour s'en apercevoir.

**Fonctions concernées :**

| Cron | Planification | Rôle métier | Impact si le secret manque |
|---|---|---|---|
| `/api/cron/reminders` | `0 9 * * *` | Relance les dossiers `DOCUMENTS_NEEDED` de plus de 7 jours | Aucune relance client — dossiers dormants |
| `/api/cron/sla-check` | `0 */2 * * *` | Alerte sur les dossiers hors SLA (4 h / 24 h / 48 h) | Aucune alerte de retard de traitement |
| `/api/cron/affiliate-purge` | `0 3 * * 0` | Supprime les clics d'affiliation de plus de 13 mois | **Non-conformité CNIL** sur la durée de conservation |

**Correction :**

1. Vérifier dans la console Clever Cloud que `CRON_SECRET` est défini. Sinon, le générer (`openssl rand -hex 32`) et le déclarer.
2. Ajouter `-f` à chaque `curl` de `clevercloud/cron.json` pour qu'un `401` produise un code de sortie non nul et devienne visible.
3. Contrôler une exécution réelle : `curl -i -H "Authorization: Bearer $CRON_SECRET" https://finarent.com/api/cron/sla-check` doit renvoyer `200`.

## 4. Constats majeurs (P1)

### 🟠 P1-1 — Aucun framework de test automatisé

`package.json` ne déclare **ni script `test`, ni Jest, ni Vitest, ni Playwright**. Les cinq fichiers `scripts/test-*.js` sont des scripts impératifs qui affichent leurs résultats en console : ils n'ont ni assertions formelles, ni code de sortie exploitable, et ne peuvent donc pas servir de barrière en intégration continue.

Conséquence : sur ≈ 45 000 lignes, **aucune régression n'est détectée automatiquement**. Toute la validation repose sur des campagnes manuelles (les dossiers `docs/TESTS_*.md`).

**Correction :** introduire Vitest pour la logique pure (`lib/scoring.js`, `lib/simulators/*`, `lib/invoicing/numbering.js`, `lib/sepa-xml.js`, `hooks/useFinancingCalculator.js`, `lib/rateLimit.js`) — c'est le meilleur rapport valeur/effort. Puis Playwright sur les trois parcours critiques.

### 🟠 P1-2 — Les scripts de seed pointent sur un autre locataire Auth0

`scripts/seed-demo.js` et `scripts/test-all-experiences.js` codent en dur :

```js
const DOMAIN = 'dev-44jsict2grc7s0jn.eu.auth0.com';  // locataire EU
```

alors que la configuration active utilise `dev-yswlyfc44okgxe10.us.auth0.com` (locataire **US**). Les identifiants Auth0 injectés en base (`auth0|6a025639...`) ne correspondent à aucun compte du locataire courant : **les comptes de démonstration créés ne peuvent pas se connecter**.

**Correction :** lire le domaine depuis `process.env.AUTH0_DOMAIN` au lieu de le coder en dur, et régénérer les comptes de démonstration sur le locataire réellement utilisé.

### 🟠 P1-3 — Les scripts de test écrivent en base sans garde-fou

`scripts/seed-demo.js` (suppression massive puis recréation), `scripts/test-e2e.js` (création de 3 comptes et d'un dossier), `scripts/test-all-experiences.js` (création puis nettoyage par préfixe) et `scripts/test-call-centers.js` (création puis nettoyage) s'exécutent tous sur `DATABASE_URL`. Combiné à P0-1, **le risque de destruction de production est immédiat**.

**Correction :** garde-fou en tête de chaque script — refus si l'URL de base désigne un hôte de production ou si `NODE_ENV === 'production'`.

### 🟠 P1-4 — Onze vulnérabilités de dépendances, dont huit hautes

| Paquet | Version | Gravité | Nature |
|---|---|---|---|
| `sharp` | < 0.35.0 | Haute | CVE libvips (CVE-2026-33327 / 33328 / 35590 / 35591) |
| `postcss` | ≤ 8.5.22 | Haute | XSS via `</style>` non échappé ; lecture arbitraire de fichiers `.map` via `sourceMappingURL` |
| `qs` | 2.2.5 – 6.15.3 | Modérée | Contournement d'`array-limit` ; déni de service |

**Correction :** `npm audit fix` corrige les trois sans changement cassant. À intégrer au rythme de maintenance.

### 🟠 P1-5 — Retards de version majeurs

| Paquet | Actuel | Dernier | Enjeu |
|---|---|---|---|
| `@auth0/nextjs-auth0` | 3.8.0 | 4.29.0 | La v3 n'est plus le canal de correctifs de sécurité |
| `@prisma/client` / `prisma` | 5.22.0 | 7.10.0 | Deux majeures de retard |
| `next` | 15.5.20 | 16.3.4 | `next lint` est déjà déprécié et **supprimé en Next 16** : `npm run lint` cassera à la migration |

**Correction :** planifier les montées de version une par une, chacune sur sa propre branche, en commençant par Auth0 (surface de sécurité).

### 🟠 P1-6 — Intégrations de production non configurées

Clés **vides** dans la configuration active :

| Variable | Fonction rendue inopérante |
|---|---|
| `SMTP_HOST` / `SMTP_USER` / `SMTP_PASS` | **Aucun email transactionnel ne part** : confirmation de demande, alerte admin, invitation affilié |
| `RECAPTCHA_SECRET_KEY` | La vérification serveur du reCAPTCHA n'a pas lieu — formulaires publics exposés au spam |
| `BREVO_API_KEY` / `BREVO_WEBHOOK_TOKEN` | Prospection email du centre d'appels inactive |
| `STRIPE_SECRET_KEY` / `STRIPE_WEBHOOK_SECRET` | Aucun encaissement de facture possible |
| `YOUSIGN_API_KEY` | Signature électronique inerte |
| `RINGOVER_API_KEY` / `RINGOVER_WEBHOOK_KEY` | Ni appel sortant, ni SMS, ni remontée d'appels |
| `NEXT_PUBLIC_SENTRY_DSN` | **Aucune remontée d'erreur en production** — les incidents sont invisibles |
| `NEXT_PUBLIC_POSTHOG_KEY` | Aucune mesure d'usage |

C'est le constat le plus lourd en valeur métier : le tunnel de conversion est en place, mais **le client qui dépose une demande ne reçoit aucun accusé de réception**.

**Correction :** prioriser SMTP (confirmations) et Sentry (visibilité), puis reCAPTCHA, puis les intégrations métier selon le calendrier commercial.

### 🟠 P1-7 — `.env.example` désynchronisé du code

- **Documente ce qui n'existe plus** : `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY` ne sont **référencés nulle part** dans le code. `lib/storage.js` bascule de Cellar vers le système de fichiers local, sans Supabase.
- **Omet ce qui est lu** : `NEXT_PUBLIC_CLARITY_PROJECT_ID` (`components/providers/ClarityTracker.jsx`) et `CELLAR_REGION` (`lib/storage.js`).

Un nouvel arrivant configure donc un service inutile et en oublie deux.

### 🟠 P1-8 — Changer le rôle d'un utilisateur depuis le back-office est sans effet durable

**Fichiers** : `lib/users.js`, `app/api/admin/users/[id]/route.js`, `scripts/promote-admin.js`, `middleware.ts`

`syncUser()` réécrit le rôle **à chaque appel**, à partir du claim Auth0, avec `CLIENT` comme valeur par défaut :

```js
const roleClaim = auth0User[ROLE_CLAIM] ?? auth0User[LEGACY_ROLE_CLAIM];
const role = roleMap[roleClaim] || 'CLIENT';
return await prisma.user.upsert({ ..., update: { ..., role }, ... });
```

Cette fonction est appelée par huit routes — `/api/notifications`, `/api/applications`, `/api/documents/*`, `/api/financement` — ainsi que par `loadCallCenterUser()`.

Or `PATCH /api/admin/users/[id]` écrit le rôle **uniquement en base**, sans jamais mettre à jour l'`app_metadata` Auth0. `scripts/promote-admin.js` fait de même.

**Conséquence :** promouvoir quelqu'un en `ADMIN` depuis `/admin/users/[id]` ou via le script fonctionne… jusqu'à ce que la personne visite n'importe quelle page appelant `syncUser`. Son rôle **retombe silencieusement à `CLIENT`**. Le back-office affiche pourtant un sélecteur de rôle qui laisse croire le contraire.

S'ajoute une incohérence de source : `middleware.ts` autorise `/admin` d'après le **claim Auth0**, tandis que `lib/auth.ts::requireAdmin` vérifie le **rôle en base**. Les deux ne peuvent concorder que si Auth0 émet bien le claim.

**En pratique, la source de vérité des rôles est l'`app_metadata` Auth0** ; la base n'en est qu'un miroir. Ce n'est écrit nulle part.

**Correction :** faire écrire `PATCH /api/admin/users/[id]` dans l'`app_metadata` Auth0 via la Management API, en plus de la base. À défaut, retirer le sélecteur de rôle du back-office et documenter que l'attribution se fait exclusivement dans la console Auth0.

### 🟠 P1-9 — `README.md` décrit une architecture qui n'existe plus

Le README parle d'**EmailJS** (remplacé par Nodemailer/Brevo), d'un dossier de build `dist/` (c'est `.next/standalone`), d'un script `npm run preview` (inexistant), et recommande un déploiement **Vercel ou Netlify** (c'est Clever Cloud). Il ne mentionne ni PostgreSQL, ni Prisma, ni les rôles, ni les 92 routes API, ni les crons.

C'est le premier fichier lu par un nouvel intervenant : en l'état, il l'oriente à l'opposé de la réalité.

## 6. Points forts

Ces éléments sont au-dessus de ce qu'on observe habituellement et méritent d'être préservés.

**Contrôle d'accès.** Les gardes `requireAuth` / `requireAdmin` / `requirePartner` / `requireInsurer` sont appliqués sur 57 routes. La vérification route par route des 92 points d'entrée n'a **révélé aucune route d'administration sans garde**. Le cloisonnement du centre d'appels (`canManageProspect` : un agent ne voit que ses prospects, un manager ceux de son centre) est implémenté côté serveur, pas seulement dans l'interface.

**Défense en profondeur.** Chiffrement AES-256-GCM des données sensibles (`lib/crypto.js`), garde anti-SSRF sur les appels sortants (`lib/ssrf-guard.js`), garde anti-traversée de répertoire sur le stockage (`lib/storage.js`), comparaison à temps constant pour les secrets de cron (`lib/cron-auth.js`), signature vérifiée sur les webhooks Stripe et Ringover.

**En-têtes HTTP.** HSTS avec `preload`, `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy` — l'ensemble est en place dans `next.config.js`.

**Qualité statique.** `tsc --noEmit` : **0 erreur**. `next lint` : **0 avertissement**. Sur 45 000 lignes en JS/TS mixte, c'est notable.

**Robustesse du déploiement.** `scripts/build.js` documente explicitement pourquoi le repli `prisma db push --accept-data-loss` a été retiré : il effaçait des colonnes de `Application` à chaque mise en ligne. L'incident ne peut plus se reproduire silencieusement — un échec de migration est désormais visible.

**Conformité RGPD outillée.** Export de données, suppression de compte, journal `RgpdAction` horodaté avec IP et user-agent, purge programmée des clics d'affiliation à 13 mois (recommandation CNIL), gestion du consentement (`lib/consent.js`).

**Traçabilité.** `AdminActivityLog`, `StatusHistory`, `DocumentAccess`, `AffiliateAuditLog`, `EmailLog` — les actions sensibles laissent une trace exploitable.

## 8. Addendum du 9 septembre 2026 — constat révélé par les tests

### 🟠 P1-10 — `nextBusinessDay()` renvoie le jour même, parfois un dimanche

**Fichier** : `lib/sepa-xml.js` · **Découvert par** : le premier test unitaire écrit sur ce module (action 2.8)

La fonction calcule le jour ouvré suivant en **heure locale** (`setDate`, `getDay`) puis sérialise le résultat en **UTC** via `toISOString()`. À minuit heure de Paris (UTC+1/+2), la date UTC est celle de la veille : le décalage annule le « +1 jour » et défait la logique d'évitement du week-end.

Comportement constaté en `Europe/Paris` :

| Jour de départ | Attendu | Réellement renvoyé |
|---|---|---|
| Lundi 07/09 | mardi 08/09 | **lundi 07/09** — le jour même |
| Jeudi 10/09 | vendredi 11/09 | **jeudi 10/09** — le jour même |
| Vendredi 11/09 | lundi 14/09 | **dimanche 13/09** |
| Samedi 12/09 | lundi 14/09 | **dimanche 13/09** |

**Portée** : `app/api/admin/affiliates/sepa/route.js` appelle `nextBusinessDay()` comme valeur par défaut de `execDate`, qui alimente `<ReqdExctnDt>` — la date d'exécution demandée du lot SEPA. Tout fichier généré sans date explicite portait donc une date déjà passée, ou un dimanche. Une banque rejette ou diffère un lot dans ce cas, et le versement des commissions d'apport échoue sans message clair côté plateforme.

**Statut** : ✅ **corrigé** le 9 septembre 2026 — sérialisation depuis les composantes locales (`getFullYear` / `getMonth` / `getDate`) au lieu de `toISOString()`. Couvert par trois tests dans `tests/unit/facturation-sepa.test.js`.

> Ce constat illustre exactement ce que P1-1 dénonçait : le défaut existait depuis l'écriture du module, ne se manifestait qu'en production, et a été révélé en quelques minutes par le premier test unitaire posé dessus.
